How a timed machine is written

Four lines on a program, one on the machine.

A program's time is written in the same file as everything else about the machine, in the same language, and checked by the same court before anything boots. There is no configuration of a scheduler and no priority to pick: four numbers say what the program needs, one number says what the machine has, and the kernel is derived from them.

What you write

A period, a deadline, a runtime and a core.

machines/qemu_deadline.machine, the part that gives time
-- on the machine: how many cores it has
DEFINE MACHINE qemu_deadline AS (
  PROFILE hosted, ARCH x86_64, KERNEL linux, CONSOLE "/dev/ttyS0",
  CORES 2
) RATIONALE "..."

-- on a program: the four together, or none
DEFINE SERVICE control AS (
  RUN ["/harb", "reserved", "--stay", "/run/control.ready"],
  RESTART always, READY "/run/control.ready",
  PERIOD 1000,
  DEADLINE 500,
  RUNTIME 200,
  CORE 1,
  NEEDS [process]
) RATIONALE "..."

PERIOD is how often the program's work comes round, in microseconds: every 1000 here, a thousand times a second. DEADLINE is by when, inside each period, the work must be done: within 500. RUNTIME is how much of the processor the kernel reserves for it in every period: 200 microseconds, a fifth of the core. CORE is which core, and the court refuses core 0, which is the machine's own: the first program, the watchdog's feed and every program that reserves nothing run there. CORES on the machine says how many cores it has; the emulator is handed the count, and a board has what it has.

From these the machine derives the rest: a kernel built to be interrupted almost anywhere, with fine timers; a reserved core set apart before the first program runs; and the reservation itself, handed to the program in the moment between its creation and its first instruction, with the rule that whatever it starts runs unreserved. The program may not ask the kernel for any of this: the call that would is refused to every program on every machine.

What the court refuses

Before anything boots, with the line named.

  • One number without the others. A reservation is a period, a deadline, a runtime and a core, together; a period alone is not one, and a core alone is a preference the kernel holds nothing to.
  • Numbers that contradict each other. A runtime longer than its deadline cannot run in the time it has, and a deadline past the period is a deadline in another period.
  • A period the kernel would not hold. From 100 microseconds to 4194304, which are the kernel's own bounds; the first draft of this rule said ten seconds, and the kernel refused it at the act.
  • A core the machine does not have, or core 0. A reservation names a core the machine declared, numbered from 0, and never the machine's own.
  • A ceiling beside a reservation. A program may be limited to a share of the processor or reserved a share of it, not both: the two say opposite things about the same time.
  • More than a core gives. The reservations of one core together ask no more than 90 per cent of it. The kernel admits 95, and since its version 6.12 it keeps 5 of those for the ordinary programs' own scheduler, in the same ledger; the court found that out when two programs asking 95 together were refused the second at boot.
harb check, on a machine edited two ways
# second asked for 750 of every 1000 us beside control's 200
machine (line 70): the reservations on core 1 ask 95.0 % of it, and the kernel gives reservations 90 % of a core: it keeps 5 % for what is not reserved and 5 % for the ordinary tasks' own server

# control asked for core 0
machine (line 61): CORE 0: core 0 is the machine's -- PID 1, the watchdog's feed and every world that reserves nothing run there

Line 70 is the program that asked too much, not the first program on the core: a refusal names the line that crossed the bound. The court counts a core's reservations the way the kernel's own admission counts them, so that what the court accepts the kernel admits, at the edge too.

Left out on purpose

What a real-time system usually has, and this one does not.

No priorities

A priority is a claim nobody checks: the kernel accepts any set of them and starves whatever is lowest. A reservation is refused when it does not fit. The floor keeps the clause the kernel can refuse, and the five calls that would let a program set a priority of its own are refused to every program.

No real-time interface

There is no scheduler for a program to call and no thread to pin. A reserved program is an ordinary program on a core set apart, with the time it was given; its loop is still its own scheduler. The reservation is the program's main thread's, and whatever it starts runs without one.

No declared timing

The kernel's model is not something you write. It is derived from the fact that a program reserves time, and read back at every boot in the kernel's own words. A machine that reserves nothing gets the calm kernel it always had, and its timers resolve to a tick.

Whose time

What a program keeps.

A program that runs as a user of its own, as a server does, is given its reservation before it becomes that user, which is the one way an ordinary user ever holds one: the kernel refuses a real-time policy to an ordinary user who asks, and the floor hands it to one who was declared it. What the program does not keep is a promise about the number: how late it actually woke is the witness's to measure, on the machine it ran on, and that is the next page.

The honest promise is time the kernel holds and a number you can read, never "real time".
