Real time

A machine that gives a program its time.

A real-time system is built on Harobanda the way any solution is: it brings its control loop, and the machine brings the time and the proof. A program declares the time it needs, the kernel keeps it on a core set apart and refuses what does not fit, and a witness measures how late each wake was. Three of its six steps are built; every boot on these pages ran in an emulator.

This is the machine above, booted: two cores, and on the second of them two programs given their time. control declared 200 microseconds of every 1000, done within 500, on core 1; the kernel's own deadline scheduler holds it there, on a core set apart for reserved programs, and would have refused it had it not fit. The kernel itself was derived from that declaration — built to be interrupted almost anywhere, with timers that resolve to the nanosecond — and the machine reads back at every boot what kernel it got. A third program with no reservation runs on the other core and gets what is left.

Can a real-time operating system be built on it? Yes — that is what the floor is for. "Real time" is two promises: that a loop runs when it should nearly always, and you can measure how nearly, which a kernel like this one keeps on a PC or a Raspberry Pi; and that it runs when it should every time, by construction, which only a microcontroller running one compiled loop can keep. A robot needs both, the first in the brain that plans and the second in the body that moves. Harobanda gives the first here, with a witness that measures it, and leaves the loop to the program that owns it: no priorities to set, no scheduler to call. The second belongs to the body's microcontroller, on MicroHaro, the edge substrate of the same project: declared here, built there, and not built yet.

Where Harobanda sits in a real-time system, from the top down:

What the machines said

Every line is quoted from a pinned boot.

A pinned boot is a transcript the repository keeps and compares, line for line, with each new run: if a machine says something else, the comparison fails. These lines are from two machines, the one above and one that measures.

a timed machine, from its pins
# the kernel, read back before any program runs
boot: timed -- the kernel is PREEMPT_RT and its timers resolve 1 ns, as it says of itself
boot: reserve -- control 200 us of every 1000 us, within 500 us, on core 1, second 700 us of every 1000 us, within 1000 us, on core 1; the kernel holds each reservation and refuses what does not fit, and signals a world that runs past its runtime once that world listens for it

# two programs ask the kernel what they run under, from inside
reserved: SCHED_DEADLINE -- 200 us of every 1000 us, within 500 us, on core 1 and no other: as the kernel reports it, signalled if it runs past its runtime, and what this world spawns runs unreserved
reserved: no reservation -- this world runs under policy 0 on 1 core, and gets what is left

# the witness, beside a program that burns the same core
tick: 1000 periods of 1000 us, deadline 500 us -- under SCHED_DEADLINE (200 us of every 1000 us), on core 1 and no other
tick: measured -- woke late by N us at the median, N us at the 99th, N us at the worst; the step took N us at the worst; N of 1000 past the deadline; signalled N times for running past its runtime

The first line is the kernel's own word about itself. The reserved program has core 1 and no other; the one with no reservation has the one other core. The last two lines are the witness, which runs its declared period on an absolute timer and says the median, the 99th, the worst, the misses, and how many times the kernel signalled it for running past its runtime: every N is a number on the screen and the letter N in the pin, because an emulator's time is the laptop's — on the one these pages were written on, about 400 microseconds late at the median and 20 milliseconds at the worst. A board gives the first number that counts.
